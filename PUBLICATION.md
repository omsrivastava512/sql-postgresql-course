# Publication queue and working agreement

## Accepted direction

SQL/PostgreSQL first; readers know basic programming; connected articles plus separate labs; local PostgreSQL and Supabase both supported; publish as the author learns. Real engineering accounts add context and contrasting decisions.

## Current package

This first package contains the full topic inventory, teaching rules, source notebook, a SQL onramp, and six connected draft articles with independent labs. It is the opening part of the course, not the finished course and not a public release.

Suggested publishing order: onramp, foreign keys, business rules, derived values, deletion, transaction boundaries, deferred checks. Numbering gives stable links, not mandatory reading order.

## Before each article goes public

- Run the setup twice to check reset; run solution and verification from a fresh state.
- Execute it on both supported environments and record engine version, date, failures and fixes.
- Check prediction feedback and changed-context answers against actual outcomes.
- Check source attribution, dates, exact scope of company claims, and working local links.
- Have the author do the lab, revise wording in their voice, and retain clear credit for external accounts.
- Confirm a new reader can understand it without private conversations.

Publishing to a site, selecting a public license, and releasing the original private repository are separate actions. Do not publish the private repository to distribute this course; export only the course materials approved for release.

## Learning feedback

After a gap, try a variant without rereading. Record the prediction, observed behavior, explanation and remaining confusion. Use it to revise a specific passage or lab, not to assign a global "mastery" score.

A test with a second reader should examine comprehension, setup friction and transfer. Ask them to explain one changed example; do not use "Did you like it?" as the only quality measure.
