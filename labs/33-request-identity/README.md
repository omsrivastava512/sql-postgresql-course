Read [the lesson](../../articles/33-request-identity.md), then establish the [dedicated local environment](../../supabase/README.md). Commands below run from the repository root. The private environment file is `.env.auth-course`; generated user credentials stay in `.env.auth-course.json`.

## Inspect the fixture

```powershell
node --env-file=.env.auth-course labs/auth-fixture.mjs users
node --env-file=.env.auth-course labs/auth-fixture.mjs reset 33
```

Read [setup.sql](setup.sql) and [solution.sql](solution.sql). The setup supplies profiles, stores and protected memberships. The reference solution supplies two functions and two SELECT policies. Neither password hashes nor signing secrets are stored in these course tables.

Predict each alias's subject, profile and stores. Alice and Reader have North membership; Bob has South; Outsider has neither a profile nor membership. All four have Auth accounts. User UUIDs are generated by the running Auth service, so use the observed IDs rather than copying an ID from another run.

```powershell
node --env-file=.env.auth-course labs/33-request-identity/request.mjs alice
node --env-file=.env.auth-course labs/33-request-identity/request.mjs bob
node --env-file=.env.auth-course labs/33-request-identity/request.mjs outsider
node --env-file=.env.auth-course labs/33-request-identity/request.mjs anon
```

For Alice and Bob, expect different actors and the same `authenticated` database role. Each sees their own profile and store. Outsider has an authenticated actor but empty profile/store results. `anon` sends no user token: expect role `anon`, actor NULL and empty private results. Record each HTTP status as well as its body. The caller does not print access tokens.

## Locate the verifier

Read [request.mjs](request.mjs). Find the password-login request, the `apikey` header and the separately attached bearer token. Explain why changing the JavaScript `alias` label cannot authorize another account. Then use the administrator SQL connection to run:

```sql
SELECT current_user, session_user, auth.uid();
SELECT pg_get_functiondef('auth.uid()'::regprocedure);
```

Record the actual role and NULL subject in a session without request claims. Read the helper's implementation: which session setting does it consume? Explain which earlier service validated that value on the HTTP path. Administrative SQL and an ordinary user API request are different evidence.

The full integration checker tests a wrong password, altered signature and genuine expiry. Do not paste a token into a public decoder or modify the expiry claim and call that a valid expired token: modifying signed claims creates a signature test instead. The local fixture's short lifetime exists so the original, unmodified token can actually expire.

## Repair the missing fact

In the administrator connection, delete only Alice's display profile:

```sql
DELETE FROM course_auth33_api.profiles WHERE display_name = 'alice';
```

Run Alice's request command again. Predict: the actor is still Alice, the profile is absent, and North is still visible. Check that membership separately. This model does not make profile completeness a condition for store admission.

Reset lesson 33, then change the authority instead:

```sql
UPDATE course_auth33_private.memberships SET active = false
WHERE actor = (
    SELECT user_id FROM course_auth33_api.profiles WHERE display_name = 'alice'
);
```

Alice still signs in and reads her profile, but the store list is empty. Restore the fixture with `reset 33`. State which of these two failures requires profile repair and which requires an authorized membership decision. Creating another Auth account is not the repair for either one.

## Independent transfer

A library adds East Library and West Library. Alice may enter East; Bob may enter West. Both retain their original store memberships. Profiles must not grant branch access. Add the two library rows and the two admissions using the existing fixture structure, without hard-coded Auth UUIDs. Predict Alice's and Bob's full ordered store lists and Outsider's result.

First hint: a branch name belongs in `stores`; a person's admission belongs in `memberships`. Second hint: the existing profiles identify the two synthetic accounts by their supplied display names during this administrative fixture task. Production display names are not immutable identity.

After your attempt, compare [transfer.sql](transfer.sql). Run the reference from a freshly reset lesson. Alice should see East Library and North; Bob should see South and West Library; Outsider should see neither branch. Explain why editing a profile or user metadata cannot substitute for either membership insert. Keep the first point where you used a hint with your predictions.
